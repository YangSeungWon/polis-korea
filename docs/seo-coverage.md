# 색인 수집 — 우리가 낸 것과 Google이 받은 것

## 왜 별도 층인가

`tests/test_sitemap.py`는 **우리가 낸 것**을 검사한다 — 5,027쪽이 sitemap에 있고,
모든 URL이 실재하고, 층 파일이 커밋 범위에 들어가는가. 2026-07에 2,190쪽이
'크롤링됨 - 색인 생성되지 않음'으로 묶였을 때 이 검사는 전부 초록이었다
(`docs/page-map.md` gap-5). 낸 것과 받은 것은 다른 사실이고, 후자는 저장소 안에
없다.

이 문서는 후자를 가져와 시계열로 쌓고, 되돌아가면 빨갛게 만드는 층을 설명한다.

## 쿼터가 설계를 정한다

| API | 쿼터(속성당) | 답하는 것 |
|---|---|---|
| URL Inspection | **2,000/일**, 600/분 | "이 URL이 색인됐나" — `coverageState` |
| Search Analytics | 1,200/분, **25,000행/요청** | "이 URL이 검색에 나타났나" |

노출 ≥1이면 색인된 게 **확정**이다(색인 안 된 쪽은 결과에 못 뜬다). 그래서 순서가
정해진다:

```
sitemap 5,027쪽
 ├─ 최근 90일 노출 ≥1  →  색인 확정. Inspection 쓸 필요 없음   → pages_seen.json
 └─ 노출 0            →  Inspection 대기열 (하루 2,000건이면 이틀) → inspect_queue.txt
```

Analytics를 먼저 돌리면 요청 한 번으로 색인 확정분을 전부 걷어내고, 남은 쪽에만
쿼터를 쓴다. 반대로 하면 인물 4,340쪽에 쿼터를 다 쓰고도 표본 오차만 남는다.

> ⚠️ **역은 성립하지 않는다.** 노출 0은 미색인의 증거가 아니라 **후보**다 — 색인
> 됐지만 한 번도 순위에 못 든 쪽이 섞여 있다. 그래서 산출물 이름이 '미색인 목록'이
> 아니라 `pages_seen.json`(=본 것)과 `inspect_queue.txt`(=물어볼 것)다. 둘을 가르는
> 건 Inspection의 `coverageState`뿐이고, 그건 아직 안 붙였다.

## 무엇을 지표로 삼는가

**층별 '노출된 페이지 수'.** 클릭·노출 총량이 아니다. 우리 사이트는 선거 주기와
시사에 크게 흔들려서(지선 주간 vs 비수기) 총량 하락은 색인과 무관한 이유로 늘
발생한다. 반면 '몇 쪽이 결과에 나타났나'는 훨씬 둔하고, 그게 줄면 색인이 실제로
되돌아간 쪽에 가깝다.

기준은 **직전 4주 중앙값 대비 20% 상대 하락**이다. 절대값(예: 층별 80%)을 쓰지
않는 이유는 person 4,340쪽이 원래 노출률이 낮기 때문이다(본문 얇음 48%,
`scripts/audit/audit_seo_templates.py`). 절대선을 그으면 person은 영구히 빨갛고
나머지는 영구히 초록이라 아무 신호도 못 준다.

## 결손 모델

`docs/absence.md`를 그대로 따른다.

| 상황 | 적는 법 |
|---|---|
| 질의 성공, 층에 행 없음 | `pages: 0` — **없다** (진짜 노출 0) |
| 질의 실패 | 그 주를 **아예 안 쓴다** — 못 받았다 |
| 16개월 밖 | 영구 결손. 0으로 채우지 않는다 |

실패를 0으로 적으면 다음 주 회귀 검사가 없던 급락을 본다. 검사에 '전 층이 동시에
0인 주가 없다'가 있는 건 그 흔적을 잡기 위해서다.

GSC 보존은 16개월이다. 이 잡을 붙인 시점 이전은 API로도 못 가져온다.

## API 함정 셋

1. **`aggregationType`은 반드시 `byPage`.** 기본 `auto`는 Google이 고르는데,
   property 집계가 섞이면 층별 페이지 수가 주마다 다른 기준으로 세어진다.
2. **`page` × `query`로 층 합계를 내지 말 것.** 익명화된 희소 질의가 응답에서
   빠지므로 분해의 합이 항상 작다. 층 합계는 `dimensions: ["page"]` 단독에서만.
3. **`searchAppearance`는 다른 차원과 같이 못 쓴다.** 2단계로 묻는다 — 단독으로
   유형 목록을 얻고, 그 유형을 필터로 걸어 페이지를 본다.

`dataState`는 `final`(기본)로 둔다. `all`은 최근 1~2일 미확정을 섞고 메타의
`first_incomplete_date` 이후를 직접 잘라내야 하는데, 주간 잡이 신선도를 살 이유가
없다. 대신 확정 지연 2~3일을 감안해 창을 3일 뒤로 민다(`LAG_DAYS`).

## 구조화 데이터가 실제로 채택됐는가

`appearance.json`이 답한다. 인물 4,340쪽에 Person·BreadcrumbList를 박았지만
(page-map gap-5) **Google이 그걸 쓰는지는 지금까지 아무도 확인 안 했다.** 마크업이
있는 것과 리치 결과로 뜨는 것은 다른 사실이다. 유형 목록이 비면 채택 0이다.

## 산출물

```
data/seo/
├── coverage.json       # 주차 → 층별 {노출된 페이지 수, 노출, 클릭}. 회귀 검사의 입력
├── pages_seen.json     # 최근 90일 노출된 페이지 (= 색인 확정분)
├── inspect_queue.txt   # 노출 0인 sitemap URL (= Inspection 후보, 미색인 아님)
├── inspection.json     # 물어본 URL의 coverageState·verdict (누적·재개 가능)
└── appearance.json     # 검색 표시 형태별 노출 (구조화 데이터 채택 여부)
```

층 정의의 단일 출처는 `sitemap-{층}.xml` 자신이다. 수집기가 접두사 규칙을 다시
쓰면 `build_sitemap.py`의 `sections`와 조용히 어긋난다.

## 인증

GCP 서비스 계정 → GSC 속성 '사용자 및 권한'에 **제한된 사용자**로 추가 → JSON 키를
`secrets.GSC_SA_JSON`.

```bash
# 로컬
GSC_SA_JSON_FILE=~/gsc-key.json python scripts/fetch/fetch_gsc.py --dry-run
# CI
gh secret set GSC_SA_JSON < ~/gsc-key.json
```

속성이 도메인(`sc-domain:polis.ysw.kr`)인지 URL 접두사(`https://polis.ysw.kr/`)인지는
스크립트가 `sites.list`로 찾는다. 서비스 계정을 속성에 안 붙였으면 목록이 비고,
그 사실을 말하고 죽는다 — 조용히 0을 적지 않는다.

## URL Inspection — '노출 0'을 가르기

`scripts/fetch/fetch_gsc_inspect.py`가 `inspect_queue.txt`를 소비해 각 URL의
`coverageState`를 묻는다. 쿼터가 설계를 정한다:

- **속성당 2,000/일.** 4,870쪽이면 사흘. 그래서 **재개 가능**하다 — 결과를
  `inspection.json`에 누적하고 이미 물어본 URL은 건너뛴다. 429가 오면 멈추고
  지금까지 것을 저장한다(버리지 않는다). 100쪽마다 중간 저장.
- **층 표본.** person이 4,198로 86%라 순서대로 물으면 사흘 내내 person만 본다.
  작은 층(main·polls·history·archive·party·region 합쳐 672)을 먼저 전부 채우고
  person을 등간격으로 뿌린다. 질문이 '어느 층이 막혔나'이므로 층 하나를 완주하는
  것보다 모든 층에 답이 있는 게 낫다.

⚠️ **`coverageState`로 세지 말 것.** `languageCode`를 따라 번역돼 온다(우리는 ko:
"크롤링됨 - 현재 색인이 생성되지 않음"). 문자열로 세면 locale이 바뀌는 순간 조용히
0이 된다. 집계는 `verdict`(PASS/NEUTRAL/FAIL)로 한다.

결손: 물어본 URL만 `inspection.json`에 적는다. 안 물어본 URL은 없다 — '모른다'와
'미색인'을 같은 자리에 적지 않는다.

## 첫 측정 (2026-08-21, 1,312쪽)

물어본 것 중 **색인 6쪽(0.5%)**. 나머지가 두 갈래로 깔끔하게 갈렸다:

| | 쪽 | 뜻 |
|---|---|---|
| Google에 알려지지 않음 | 902 (69%) | URL 존재를 모름 |
| 크롤됐으나 미색인 | 402 (31%) | 2026-06에 봤고 안 실었다 (왜인지는 아래) |

층별로 갈리는 방식이 다르다:

```
region   375 / 375  전부 '알려지지 않음'
party    145 / 145  전부 '알려지지 않음'
polls      9 /   9  전부 '알려지지 않음'
person   322 알려지지 않음 · 313 크롤됨-미색인 · 3 색인
archive   60 크롤됨-미색인 · 7 알려지지 않음 · 3 색인
```

두 가지가 이 그림을 설명한다:

1. **sitemap 제출이 2026-08-20이다.** 그 전까지 발견 경로는 내부 링크뿐이었고,
   region·party·polls는 링크 깊이가 깊어 한 번도 안 걸렸다. 902쪽은 내용 문제가
   아니라 **아직 시간이 안 지난 것**이다.
2. **크롤된 402쪽 중 397쪽의 마지막 크롤이 2026-06이다.** 8월은 5쪽뿐 —
   6월 이후 Googlebot이 사실상 안 온다. 같은 6월에 `a00824e5`가 URL 300개를
   404로 만들었다(295명은 다른 주소로 생존). 시점은 겹치지만 300/4,326은 7%라
   **이것만으로 크롤 중단을 설명할 수는 없다.** 상관이지 인과가 아니다.

### 미색인의 원인을 '얇음'으로 지목할 근거가 없다

<!-- 2026-08-22에 이 자리에 "Google은 68자짜리를 보고 안 싣기로 했다"고 적었다.
     하루 뒤 site: 검색 결과가 그걸 반증했다. 아래가 정정본이다. -->

먼저 정정. 2026-06 인물 페이지의 정적 본문이 68자라 '빈 껍데기라서 안 실렸다'고
읽었는데, **틀렸다.** 내용은 `<script id="person-data" type="application/json">`에
다 있었고 Google은 그걸 **렌더해서 색인했다.** 증거는 색인된 페이지의 검색
스니펫이다 — 그 JSON에만 있던 득표율("1위 60.4% 당선")이 그대로 찍혀 있다.

그리고 같은 시점의 두 집단을 같은 잣대로 재면 차이가 없다:

```
색인됨(PASS)      9쪽 · 2026-06 정적 본문 중앙값 68자
크롤됨-미색인    368쪽 · 2026-06 정적 본문 중앙값 68자
```

**정적 본문 길이는 그 둘을 가르지 못한다.** 6월엔 전부 같은 상태였고 그중
0.4%만 실렸다. 무엇이 갈랐는지는 지금 데이터로 모른다 — 색인된 13쪽에 이낙연·
김부겸 같은 알려진 인물이 섞여 있지만 김봉재·윤병한 같은 옛 인물도 있어 한 가지로
설명되지 않고, 표본 13개로 패턴을 말하는 건 무리다.

이 정정이 남기는 것:

- **정적 렌더로 바꾼 게 무의미했다는 뜻은 아니다.** 렌더 비용 없이 읽히는 편이
  유리한 건 맞다. 다만 그게 미색인의 **원인**이었다는 근거는 관측에 없다.
  `docs/page-map.md` gap-5의 진단("본문이 HTML에 없다")도 이 눈금으로 다시 읽어야
  한다 — 본문은 파일 안에 있었고, 렌더하면 보였다.
- **측정 도구를 고쳤다.** `audit_seo_templates.py`가 `<script type="application/json">`
  페이로드를 '자료 길이'로 따로 센다. 정적 68자는 두 가지를 뜻할 수 있고 대응이
  다르기 때문이다 — 자료 0이면 진짜 빈 껍데기, 자료가 있으면 렌더 필요.
  실제로 세어보니 person 얇음 2,067쪽 중 **진짜 빈 껍데기는 3쪽**이고, party는
  얇은 18쪽이 **전부** 빈 껍데기다. 손댈 자리가 person이 아니라 party였다.
- **판정 시점은 여전히 과거다.** 인물 313쪽 중 312쪽의 마지막 크롤이 2026-06이고,
  그 뒤 `eedd49da6`(08-04)·`d631b1695`(08-19)가 들어갔다. Google은 지금 버전을
  본 적이 없다. 402가 '지금의 결함'인지는 재크롤 뒤에야 갈린다.
- **재크롤이 선행 조건이다.** 다시 안 오면 고친 내용은 평가 대상이 되지 못한다.
  지금 병목은 내용이 아니라 크롤이다.

### 다음 측정에서 볼 것

순서가 있다. 앞이 안 움직이면 뒤는 물을 수 없다.

1. **902가 줄어드는가** — 발견이 작동하는가(sitemap·내부 링크)
2. **402의 `lastCrawlTime`이 2026-08 이후로 갱신되는가** — Googlebot이 돌아오는가
3. **그중 `verdict`가 PASS로 바뀐 게 몇인가** — 두껍게 한 게 먹혔는가

2번이 0이면 3번은 아직 시작도 안 된 것이다. 그때 내용을 더 손대는 건 평가받지
못할 것을 고치는 일이 된다.
